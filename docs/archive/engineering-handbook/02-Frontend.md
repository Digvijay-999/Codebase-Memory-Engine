# Frontend Engineering

The ContextForge frontend is a Single Page Application (SPA) built with React and Vite. It serves as the visual presentation and interaction layer of the application. 

## Pages Overview

### 1. Landing Page (`Landing.jsx`)
- **Purpose:** The entry point of the application. Sells the value proposition of ContextForge.
- **Responsibilities:** Renders marketing copy, a 3D/animated hero section (using framer-motion and custom shaders), and a "Launch Workspace" button.
- **Important Components:** `HeroShader`, `SvgFollowScroll`.
- **Data Flow:** No heavy API interaction. Primarily visual state and routing. 

### 2. Dashboard (`Dashboard.jsx`)
- **Purpose:** The repository management hub.
- **Responsibilities:** Allows users to input a GitHub URL and trigger the ingestion process. Displays the list of currently indexed repositories.
- **State:** Tracks `repoUrl`, `loading` state, `status` (success/error messages), and `repos` (list of available repositories).
- **API Calls:** `api.indexRepository()` to clone and index, `api.getRepos()` to populate the list.
- **Routing:** On successful indexing, updates `localStorage` with the selected `repo_name` and redirects the user to the Chat page.

### 3. Chat (`Chat.jsx` / `AnimatedAiChat.tsx`)
- **Purpose:** The primary interaction interface where developers converse with their codebase.
- **Responsibilities:** Handles semantic Q&A as well as specialized Quick Actions (Whole Repository Analysis).
- **State:** `messages` array holding the chat history, `activeRepo` from `localStorage`, `isTyping` loader.
- **Important Components:** `AnimatedAiChat` handles the complex UI logic of the chatbox, including growing text areas, command palettes, and message rendering.
- **Data Flow:** 
  - Standard queries are routed to `api.askQuestion()`.
  - specialized "Category B" queries (e.g., Find Dead Code, Security Review) are routed to `api.analyzeRepo()` which performs whole-repository analysis.

### 4. Documentation (`Docs.jsx`)
- **Purpose:** Presents high-level architectural reports generated by the AI.
- **Responsibilities:** Automatically requests an architecture overview for the active repository on mount. Provides functionality to export this report as a `.md` file.
- **State:** `report` (the markdown string), `loading`, `repoName`.
- **API Calls:** `api.explainRepo()` on component mount.
- **Data Flow:** The returned markdown is stored in state and rendered using `ReactMarkdown`. The Export button transforms this state into a Blob and triggers a browser download.

### 5. AppSidebar (`AppSidebar.jsx`)
- **Purpose:** Global navigation menu.
- **Responsibilities:** Persistent across the Dashboard, Chat, and Docs pages to allow seamless context switching.
- **State:** Derives active state from React Router's `useLocation`.

## Data Management & State

ContextForge takes a minimalist approach to state management.
- **Global State:** Uses browser `localStorage` (specifically the `repo_name` key) to track which repository the user is currently interacting with. This ensures that when a user navigates from Chat to Docs, the application remembers the active context.
- **Local State:** Uses standard React `useState` and `useEffect` hooks for component-level data (loaders, form inputs, message arrays). 

## Styling and Animations
- **TailwindCSS:** Used exclusively for all styling. Class names are combined using a `cn()` utility (clsx + tailwind-merge) to allow conditional styling without class conflicts.
- **Framer Motion:** Used for micro-interactions (button scales, hover states) and page transitions.

> [!TIP]
> **Interview Tip:** Be prepared to explain why `localStorage` was chosen over a complex state manager like Redux or Zustand. The ideal answer is **Simplicity**: ContextForge only needs to track a single string (`repo_name`) globally. Introducing Redux for a single variable is massive over-engineering.
